# 规范知识库架构与向量化方案

## 为什么不建议直接向量化整份 PDF

一份规范包含正文、条文说明、表格、公式、页眉页脚和目录。直接切成固定长度文本会带来三个问题：

1. 条款号、板厚分组和截面型号可能被切断。
2. 同一段正文与条文说明混在一起，无法判断哪部分具有规范效力。
3. 扫描页和表格图片没有文字，向量库检索不到。

## 已采用的处理链路

```text
PDF/网页
  → 文字层抽取
  → 对无文字页或网页图片 OCR
  → 页级/节级 JSONL
  → 检索文本块
  → SQLite 全文索引 + 向量索引
  → MCP / HTTP / LangChain 工具
```

## 文本块元数据

每个文本块保留：

- `standard_id`：标准号。
- `version`：标准版本。
- `status`：现行、即将实施或修订条文。
- `page_no` 或 `section_no`：原文件页码或网页章节号。
- `clause_no`：识别到的条款号。
- `source_file`：本地原始文件位置。
- `source_url`：公开来源。
- `source_type`：文字层、PDF OCR 或网页 OCR。
- `text`：供检索的文本。

## 检索方案

当前使用：

- SQLite FTS5 全文召回，解决标准号、条款号、型号和数值的精确匹配。
- 中文字符/双字/三字与英文数字混合的哈希 TF-IDF 向量，解决同义表达和部分语义召回。
- 两路结果合并排序。
- 材料参数和截面参数使用独立结构化查询，不经过语义搜索。

## 后续升级

若需要更强语义能力，可替换为：

- 本地向量模型：BGE-small-zh-v1.5，适合普通 CPU 和本地部署。
- 高质量中文检索：BGE-M3，支持稠密、稀疏和多向量检索。
- 精排：BGE-reranker-v2-m3，对召回的前 20 到 50 条结果重排。
- 大规模服务：Qdrant、Milvus 或 Elasticsearch。

工具接口不需要因替换模型而改变。

## 推荐封装

- 智能体直接调用：MCP Server。
- 现有 Web/LangChain 服务：FastAPI 路由。
- 本地调试：命令行。
- 不推荐把整套检索逻辑写进提示词，也不推荐让大模型记忆规范数值。
